# Codex 客户端配置自定义中转代理 API 报错 401 解决方案

Date: 2026-07-06
Agent: Antigravity

## 背景 (Background)
在 Codex 客户端配置自定义模型服务商 (`model_provider = "custom_provider"`) 时，通常会在 `~/.codex/config.toml` 中配置 `base_url`、`wire_api` 并在 `http_headers` 中以 `Authorization = "Bearer sk-..."` 形式手动注入自定义的 API Key。

## 问题 (Problem)
配置完毕后，客户端请求抛出以下错误：
`■ unexpected status 401 Unauthorized: Invalid API key provided, url: https://k12.xcpcai.com/v1/responses`
但在其他机器上使用完全相同的 `config.toml` 格式与 Key 却能够正常工作。

## 解决方案 (Solution)
经过严密的网络验证与配置文件联立审查，确定了该问题的本质是由于**全局认证配置对自定义头部产生了竞态覆盖**。

1. **直接验证 API Key 有效性**：
   在本地使用 `curl` 携带相同的 `Authorization` 头直接访问目标端点：
   ```bash
   curl -i -X POST https://k12.xcpcai.com/v1/responses -H "Authorization: Bearer sk-your-api-key" ...
   ```
   接口成功通过鉴权并返回了 400 参数不支持错误（而非 401 鉴权失败）。**【事实/证据】**：API Key 自身有效，网络通畅。

2. **定位本地配置冲突**：
   检查发现 `~/.codex/` 下存在另一个配置文件 `~/.codex/auth.json`，其内容如下：
   ```json
   {
     "auth_mode": "apikey",
     "OPENAI_API_KEY": "sk-6.7-zhengbasai"
   }
   ```
   **【理论推论】**：Codex 客户端在 `auth_mode` 为 `apikey` 时，会自动加载全局的 `OPENAI_API_KEY`，并在实际发送请求时用其**重写/覆盖** `config.toml` 中配置的 `Authorization` 头。导致发出的实际 Key 为无效的 `sk-6.7-zhengbasai`。

3. **修复手段**：
   将 `~/.codex/auth.json` 里的 `"OPENAI_API_KEY"` 修改为与 `config.toml` 中一致的正确 API Key。

## 避坑指南 (Pitfalls)
1. **不要盲信 401 报错直接断定 Key 本身已失效**：
   排查时应当使用 `curl` 剔除客户端干扰，直接发送请求来确认 API Key 状态。
2. **警惕多配置文件冲突**：
   在使用自定义代理时，要注意 `auth.json` 中配置的全局变量（如 `OPENAI_API_KEY`）具有更高的修改/覆盖优先级。若需维持多机器一致，需确保全局 `auth.json` 的一致性。
3. **环境差异主观推测**：
   *【此处缺乏直接证据，属于理论/经验推测】*：另一台机器上之所以可以用，极有可能是因为那台机器的 `~/.codex/auth.json` 文件不存在，或者其内部的 `OPENAI_API_KEY` 已经正确设置。
