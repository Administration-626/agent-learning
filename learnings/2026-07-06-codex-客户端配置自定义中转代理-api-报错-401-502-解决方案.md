# Codex 客户端配置自定义中转代理 API 报错 401/502 解决方案

Date: 2026-07-06
Agent: Antigravity

## 背景 (Background)
用户尝试将 Codex CLI (v0.142.5) 与第三方 OpenAI API 兼容代理服务（如 `tokenx24.com`）对接，用于日常编码辅助。最初在 `~/.codex/config.toml` 中将 `model_provider` 配置为自定义提供商 `custom_cpa`，配合自定义模型 `gpt-5.5`。

## 问题 (Problem)
1. **协议强绑定与接口限制**：在 Codex 中使用 `gpt-5.5`（以及所有配置在自定义提供商 `model_providers.<name>` 下的模型）时，客户端强制要求底层通信协议为 `responses`（即要求使用 `/responses` 路由建立 WebSocket 或 HTTP 通道）。
2. **代理站对特定路由支持不全**：多数第三方 OpenAI 代理（如 tokenx24.com）并不对 `/v1/responses` 这一 Codex 专有接口做反代，直接返回 401（部分网关返回 502）。但在根路径 `/responses` 下（不带 `/v1`）该代理支持 WebSocket 握手升级，但在未带正确授权时也会被拒。
3. **Enum 反序列化限制**：如果在 `config.toml` 中强行将自定义提供商的 `wire_api` 改为 OpenAI 标准的 `chat/completions`，客户端会报反序列化错误 `unknown variant chat/completions, expected responses`。
4. **Key 优先级覆盖机制**：客户端在使用全局 `openai` 提供商时，即便传入了环境变量 `OPENAI_API_KEY`，客户端也会无视并强制优先使用 `~/.codex/auth.json` 中已存的旧 API key，导致即使更换了有效 Key 也依然因为读到了失效的旧 Key 而持续报 401 错误。

## 解决方案 (Solution)
1. **替换全局密钥**：直接在 `~/.codex/auth.json` 中将 `"OPENAI_API_KEY"` 的值更新为最新有效的代理 API Key（在本案中为 `sk-6.7-zhengbasai`）。
2. **劫持官方 OpenAI 提供商的路由**：在 `~/.codex/config.toml` 中，将 `model_provider` 设为官方的 `"openai"`，从而不再使用自定义块；同时利用顶级配置参数 `openai_base_url = "https://tokenx24.com"`（**必须是根路径，不带 /v1**）来劫持官方提供商的请求底座。
3. **使能 WebSocket responses 通道**：通过以上配置，Codex 会加载 `auth.json` 中的新 API Key 并向 `wss://tokenx24.com/responses` 进行正常的 WebSocket 握手升级（状态码 101），从而完美绕过代理站对 `/v1/responses` 的拦截或缺失，实现了 `gpt-5.5` 高级特性的全功能通畅调用。

## 避坑指南 (Pitfalls)
1. **避免使用 `[model_providers.<custom>]` 块配置第三方兼容代理**：因为 Codex 客户端的自定义提供商配置仅允许 `responses` 协议，如果代理站对 WebSocket /responses 转发有 Bug，将陷入 401/502 循环。
2. **清理本地 `auth.json` 遗留密钥**：更新配置时必须全局清空或替换 `auth.json` 内的残留密钥。Codex 内部的 Key 读取优先级往往高于终端环境变量 `OPENAI_API_KEY`，只修改环境变量可能会导致静默失效。
3. **区分 `base_url` 的路径结构**（此处基于经验推测，可能与代理站的网关路由转发和 Headers 头部过滤机制有关）：根路径 `https://tokenx24.com` 用于 WebSocket 握手时拼接 `/responses`；如果错误配置成了 `https://tokenx24.com/v1`，就会强制去请求 `/v1/responses` 路由而报错。
